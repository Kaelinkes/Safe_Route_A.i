# Phase 5 implementation notes and honest readiness assessment

## Implemented in this working package

1. Preserved the supplied LightGBM `.joblib` bundle and its 12-feature contract.
2. Added `/predict-route`, which requests Open-Meteo current/hourly weather for every supplied route coordinate, chooses current conditions for near-now arrival times and hourly forecast otherwise, and maps WMO weather codes/lighting into the legacy model's categories.
3. Explicitly requests Open-Meteo units: °C, km/h and mm; retains visibility in metres and radiation in W/m².
4. Removed silent speed clipping. 120 and 130 km/h remain distinct after conversion, and out-of-training-range values are returned with a warning.
5. Added separate approved-community-report scoring with approval, severity, distance and recency checks. Original ML score and community overlay score are returned separately.
6. Added native LightGBM feature-contribution explanations where available.
7. Added validation for missing fields, invalid categories, invalid numeric values, invalid coordinates and empty/oversized batches.
8. Reworked training to compute risk cutoffs after the train/validation split, exclude ID/target from predictors, remove exact duplicates, and optionally compare XGBoost on the same split.
9. Added automated tests for API validation, route-wide weather mapping, current/hourly selection, community reports and non-clipping speed conversion.

## Verification performed

- The original joblib bundle loads successfully and exposes 12 expected model features.
- Automated tests are run with `pytest -q` (see the delivered test results when available).
- Open-Meteo network calls are tested using deterministic mocked HTTP responses. A live external request has not been claimed as tested in this build environment.

## Not yet complete / requires source data or team decisions

- The original Kaggle `train.csv` was not included in the uploaded ZIP. Therefore no retraining, additional cleaning, or new accuracy claim has been produced.
- The Kaggle competition describes its data as generated by a deep-learning model trained on a simulated road-accident dataset. It is not South African ground-truth validation.
- The original speed-limit unit is not verified from the missing CSV/data dictionary. The legacy code assumed mph. The revised mapper avoids clipping and flags values beyond the bundle's numeric range, but this does not make 120/130 km/h predictions validated. Retrain after confirming units and local feature coverage.
- South African accident data has not yet been downloaded, licensed, harmonised or evaluated. A quick schema review of the Cape Town 2019–2024 ArcGIS layer found a table without geometry/coordinate fields, so it is not a ready-made route-coordinate validation dataset.
- Community blend weight, report radius, severity weights and recency half-life are provisional engineering defaults. They need domain-owner agreement and calibration against labelled local outcomes.
- Open-Meteo is a forecast/reanalysis provider, not a roadside sensor. Forecast quality and availability vary by location/time. Production use needs caching, retries, rate limits and monitoring.
- Full ASP.NET integration cannot be tested until the other team shares its API/route payload contract. The provided endpoint contract is ready for review with them.
- Geographic/time-based model validation and leakage audit require source data with suitable identifiers/timestamps. Current Kaggle validation is random holdout only.
